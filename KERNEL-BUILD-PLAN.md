# `linux-jarvisos` Unified Kernel Build & KVM Test Plan

Integrates CachyOS 7.3, Omarchy desktop tuning, and `JarvisOSLinux` drivers cleanly for **HP Intel Core i5-1235U** (Alder Lake, `7.4 GiB` RAM, Iris Xe, Intel SOF Audio, Realtek RTL8822CE).

## Corrections Over Prior Draft

- Removed nonexistent Kconfig symbols (`CONFIG_HDA_GENERIC`, `CONFIG_X86_HYBRID_CPUS`, `CONFIG_HWP_EPP`) and replaced them with valid Intel Alder Lake symbols (`CONFIG_SND_HDA_GENERIC=m`, `CONFIG_SND_SOC_SOF_ALDERLAKE=m`, `CONFIG_SCHED_MC_PRIO=y`, `CONFIG_X86_INTEL_PSTATE=y`).
- Disabled `CONFIG_RUST`, `CONFIG_DEBUG_INFO_DWARF5`, and `CONFIG_DEBUG_INFO_BTF` (`CONFIG_DEBUG_INFO_NONE=y`) and defaulted to `localmod.db` (`_localmodcfg=yes`) so builds stay safely inside `7.4 GiB` RAM without `pahole` OOMs.
- Bounded default build concurrency to `_jobs=1` and `CPU_QUOTA=60%` in [build-kernel.sh](scripts/build-kernel.sh) to stay under `jarvis-monitor`'s `80%` process CPU cutoff.
- Kept `CONFIG_DIBS=y` so `jarvis.ko` loads standalone without external `dibs.ko` dependencies.
- Documented `jarvis_policy.c` accurately as an opt-in ioctl policy table until your `~/JARVIS OS` userspace calls `/dev/jarvis` (and note `jarvis_keys` currently enforces `CAP_SYS_ADMIN`).

## JARVIS OS Kernel 1.0 release checks

The Arch package version is `1:1.0-1`. Epoch `1` makes it an upgrade from `7.3.6-1`. Linux still identifies its ABI as `7.3.6-1-jarvisos1.0`; never rename an old module directory to this release. The default local-module profile targets this HP laptop, not arbitrary x86-64 hardware.

1. Build as an unprivileged user with the listed dependencies already installed. `./scripts/build-kernel.sh` checks inputs and invokes `makepkg`; it does not install dependencies or packages. For a published release, use `./scripts/build-kernel.sh --sign --key <approved-key-fingerprint>` on the release signer. Pin and authenticate that fingerprint separately. BLAKE2 source checksums, package digests, and an autogenerated kernel module signature do not authenticate the publisher.
2. Get the exact two archive paths with `PKGDEST="$PWD/out" makepkg --packagelist`. Run `./scripts/test-package-kvm.sh <kernel-package> <headers-package>` on those archives, not on the installed module or an external test build. The gate rejects private signing material, requires packaged `CONFIG_MODULE_SIG_FORCE=y`, and proves `sig_enforce=Y` without adding an enforcing boot argument. Keep the digests, guest verdict and both archives together.
3. Run `./scripts/test-kvm-full-os.sh <kernel-package>` against a clean disposable copy of the target VM. Release mode requires a detached archive signature trusted by the guest's pacman keyring. `ALLOW_UNSIGNED_LOCAL=1` exists only to prove pre-release boot functionality and prints `FUNCTIONAL PASS (UNSIGNED; NOT RELEASE)`. Keep the physical host's rollback packages. A direct-kernel VM boot does not exercise the laptop's firmware, bootloader, encrypted-root hook or UKI.
4. Before deployment, verify published signatures under the intended trust policy. On this host, make the root-owned `zz-jarvis-encrypt.conf` select JARVIS kernels by their packaged `pkgbase`, not one exact kernel release, before the package transaction generates a UKI. Ask the operator before changing that boot configuration, installing, reloading a module, or rebooting. After authorized deployment, compare the installed file's digest and running module identity to the tested package, require `sig_enforce=Y`, and verify the active boot entry. Do not run the policy-reset stress test on the host.
